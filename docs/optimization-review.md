# 项目检查与优化建议

检查日期: 2026-09-24. 范围: `app/` 的 API, 任务执行, Speaker 同步, 模型管理和数据库查询. 下列条目保留修复前的检查依据, 链接中的行号对应检查时的版本. 当前实现已落地对应改进, 数据库统一使用 PostgreSQL, 访问控制采用管理员创建账号、Bearer Token 和用户任务归属; 接口与部署方式见 [API 文档](api.md) 和 [README](../README.md). 模型就绪检查验证必需文件存在且非空, 不验证权重文件哈希. 多进程全局队列不在当前单进程部署范围内.

## 优先处理

### 1. 任务从线程写入 `asyncio.Queue`

- 证据: [API 在工作线程创建任务](../app/api/jobs.py#L11-L23), [工作线程直接调用 `put_nowait`](../app/services/job.py#L13-L29), [事件循环等待队列](../app/services/tts.py#L107-L113).
- 影响: `asyncio.Queue` 不支持跨线程操作. 本地 Python 3.12.13 按当前 `to_thread` 调用方式复现时, 普通模式下任务能被及时唤醒, 但事件循环调试模式会抛 `RuntimeError: Non-thread-safe operation invoked on an event loop other than the current one`. 此时任务已经写入数据库, 请求却会失败.
- 建议: 在线程内只完成阻塞的数据库写入, 回到事件循环线程后入队. 同时为数据库已写入但未成功入队的任务提供恢复机制. 验收时在普通模式和事件循环调试模式下覆盖队列空闲后的首次提交.

### 2. 重启后未恢复未完成任务, Worker 异常会停止消费

- 证据: [启动时只初始化数据库并启动 Worker](../app/main.py#L14-L22), [任务只存在于进程内队列](../app/services/tts.py#L13-L14), [Worker 缺少异常处理和 `task_done` 的 `finally`](../app/services/tts.py#L107-L113), [数据库读写可能在 `run_job` 的 `try` 外抛错](../app/services/tts.py#L47-L56).
- 影响: 进程重启后数据库中的 `pending` / `running` 记录不会重新入队. 一次未处理的数据库或模型外层异常会结束唯一的 Worker, 后续任务持续排队. 这也使多进程部署无法维持全局单任务推理约束.
- 建议: 启动时按明确规则恢复或标记未完成任务; 为 Worker 增加顶层异常记录和 `finally: task_done()`, 并监控任务是否存活. 若需要多进程, 再引入共享队列和全局执行锁. 验收时模拟重启和一次 Worker 异常.

### 3. 缺少头像路径时任务查询返回 500

- 证据: [`icon_path` 在数据库中允许为空](../app/db/database.py#L29-L38), [同步时可写入 `None`](../app/services/sync.py#L104-L112), [列表和详情对值直接调用 `.format()`](../app/services/job.py#L32-L74). Speaker 查询已有[空值处理](../app/services/speaker.py#L8-L33).
- 影响: 合法的无头像 Speaker 关联任务后, `GET /api/jobs` 和 `GET /api/jobs/{id}` 都会抛 `AttributeError`. 本地用 `icon_path=None` 调用详情服务已复现.
- 建议: 仅在路径非空时替换 `{id}`, 否则返回 `speaker_icon_url=null`; 两个调用点保持一致. 验收时分别查询无头像 Speaker 的任务列表和详情.

### 4. 模型空闲判断未考虑正在执行的任务

- 证据: [模型使用时间在推理开始前更新](../app/services/tts.py#L23-L30), [Worker 取出任务后队列可为空](../app/services/tts.py#L107-L113), [监视器只检查队列和时间](../app/services/tts.py#L116-L125).
- 影响: 单次生成超过 180 秒且没有待处理任务时, 监视器会在推理仍运行期间执行卸载流程. 当前局部变量仍引用模型, 但全局状态被清空并执行显存清理, 后续任务可能重复加载模型.
- 建议: 显式记录正在执行的任务, 仅在 Worker 空闲且队列为空时卸载; 在任务结束后更新最后使用时间. 验收时用慢生成替身跨过空闲阈值.

### 5. Speaker 同步的下载路径可能越出本地目录

- 证据: [远端 key 去掉前缀后直接拼到本地路径](../app/services/sync.py#L28-L41). 当前过滤会跳过 `..`, 但不会跳过以 `/` 开头的相对片段或本地目录中的符号链接. 例如默认前缀下的 key `speaker//tmp/zvox-probe` 会得到本地路径 `/tmp/zvox-probe`.
- 影响: 若不可信主体能写入 S3 Speaker 前缀, 下一次同步可能在 `SPEAKER_DIR` 外创建文件; 实际可写范围受服务进程权限限制.
- 建议: 拒绝绝对路径和非预期路径组件, 在下载前验证解析后的目标仍位于 `SPEAKER_DIR` 内, 并考虑符号链接. 验收时覆盖前导 `/`, `..` 和符号链接目录.

### 6. 对外部署时管理接口和任务内容缺少访问控制

- 证据: [管理路由没有鉴权依赖](../app/api/admin.py#L6-L41), [任务列表和详情也没有访问控制](../app/api/jobs.py#L26-L38), [全来源 CORS](../app/main.py#L25-L31). 任务详情包含提交 IP, 文本及错误信息, 任务 ID 可由列表接口获得.
- 影响: 服务若可被不可信客户端访问, 任意访问者可触发模型下载和 S3 同步, 枚举任务文本并读取提交 IP. 创建任务接口也可被反复调用占用推理资源.
- 建议: 明确部署边界. 对公网部署, 为管理接口加认证, 为任务列表和详情增加授权与必要的数据最小化, 并限制提交速率; 若只在可信内网使用, 在网关限制访问范围. CORS 只控制浏览器访问, 不能替代鉴权.

## 后续优化

### 7. 失败时临时 WAV 文件可能残留

- 证据: [创建临时文件后, 仅在上传成功后删除](../app/services/tts.py#L71-L81).
- 影响: 写文件或上传失败会留下临时 WAV, 持续失败可能耗尽磁盘空间.
- 建议: 用 `try/finally` 清理已创建的路径. 验收时让音频写入和 S3 上传分别失败, 确认临时文件消失.

### 8. 同步元数据出错时可能误删 Speaker, 状态也可能失真

- 证据: [JSON 解析失败被静默跳过](../app/services/sync.py#L78-L94), [随后删除所有未出现的 ID](../app/services/sync.py#L115-L122), [状态先置为非运行再更新数据库](../app/services/sync.py#L64-L67). 非法 `id` 在 `int()` 处抛错且不会进入 `last_result.errors`.
- 影响: 现有 `vox-data.json` 损坏时, 原有 Speaker 记录可能被删除; 更新数据库失败时, 状态仍可能显示同步结束且没有对应错误.
- 建议: 先完整解析和校验所有元数据, 有错误时保留原有记录并报告失败; 在事务完成后更新同步状态. 验收时覆盖坏 JSON, 非法 ID 和数据库写入失败.

### 9. 任务列表的查询次数和排序成本随数据增长

- 证据: [每条任务单独查询 Speaker](../app/services/job.py#L32-L50), [任务列表按 `created_at` 排序](../app/db/database.py#L90-L104), [建表时没有相应索引](../app/db/database.py#L14-L41).
- 影响: 修复前 `limit=100` 时至少执行 101 次数据库查询, 且列表排序缺少对应索引, 查询成本随数据量增长.
- 建议: 用一次 `LEFT JOIN` 获取列表所需的 Speaker 字段, 并给 `jobs(created_at)` 建索引. 数据量增长后再评估游标同时间戳的稳定性. 验收时比较查询计划和列表返回内容.

### 10. 模型就绪检查只判断目录非空

- 证据: [`check_model()` 只检查目录存在且有任意文件](../app/services/model.py#L18-L21), [下载状态接口先调用该检查](../app/api/admin.py#L25-L41).
- 影响: 部分下载或损坏的模型目录会被报告为 `ready`, 后续加载才失败; 下载线程仍运行时也可能提前显示就绪.
- 建议: 以下载完成标记或模型必需文件的完整性校验判断就绪, 并先呈现进行中的下载状态. 验收时在仅有单个文件的模型目录查询状态.

## 验证范围与实施顺序

原始检查只阅读代码并运行隔离的只读复现, 未连接 S3 或运行 VoxCPM 推理. 修复后新增 `tests/test_regressions.py`, 覆盖鉴权与归属、任务恢复、路径检查、元数据校验、模型必需文件、Worker 异常和临时文件清理. 数据库回归使用 PostgreSQL 独立随机 Schema. 仍未进行真实 S3 和 GPU 推理集成测试.

单进程部署是当前设计约束. 若未来增加多个 Uvicorn Worker, 需要共享任务队列与全局推理锁.
